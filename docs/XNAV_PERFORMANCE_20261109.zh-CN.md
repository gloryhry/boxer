# img7 第二轮性能优化与验收

本轮基线是 2026-11-09 开始实施时的完整工作区，包含第一轮优化及全部未提交源文件修改。源文件与 SHA-256 清单位于 `../../diagnostics/performance-20261109/source-before`、`baseline-manifest.json`；没有回退到第一轮优化之前的版本。

验收目标为相对该同期基线整张 img7 耗时中位数再降低至少 10%，同时 img2 不出现稳定回退。历史的 544.41 秒仅供参考，不作本次基线。

最终样本验收通过：完整 img7 三次耗时中位数由 **329.096 降至 288.744 秒（降低 12.26%）**，img2 由 **233.496 降至 223.465 秒（降低 4.30%）**；全部业务结果和六个 CSV 严格一致，功能、关联、退出和缓存验证均完成。共享主机的单次结果波动较大；这些数字按约定的两版本中位数之比计算，不代表每次运行都至少降低 10%。最终判据汇总为 `final-validation.json`。

## 改动与不变量

- 一个 `xnav-output-ack` 线程独占输出进程的消息接收。输出进程仍在可靠写入完成后发送 `committed`；只有这条 ACK 能触发内部 `on_durable` 并释放推理额度。主线程从容量 4 的本地队列处理原 `on_commit`、结束和异常消息。重复 ACK 不重复释放，乱序或未知 ACK 报错。
- 推理额度仍为 2。输入、输出队列原上限不变。关闭接收线程会打断本地队列写入；正常收尾先处理全部 ACK，再处理终止消息。停止或异常不会把未提交帧视作已持久化。
- 文本通过一次 `tolist()` 读取编码，再执行原来的整数转换、非法 Unicode 过滤、去尾部空白；原标签大小写处理不变。
- 历史观测相机和位姿在首次使用时上传并缓存。投影仍按相机张量尺寸分组，并保留每组的视图顺序与批次形状。同组相机模型一致时复用 CPU 已知标签，避免 CUDA `unique().tolist()` 与索引回读；混合模型保留原分派。独立图像观测没有因共享 LiDAR 锚点而被合并或省略。
- 原始 Monte Carlo IoU 按两个框的完整几何有向配对缓存，最多 512 项。只缓存数值，语义、证据、阈值、代表框和历史成员的兼容性仍逐次判断。框变化会形成新几何键，`reset()` 清空缓存。
- 全组均为 PolynomialCamera 时使用通过完整整图对照的 64 轨迹 CUDA 门槛；其他相机与混合组仍为 256。串行和 `force_cpu` 保留 CPU 参考，原 CPU 边界修复不变。
- 历史观测中的纯 PolynomialCamera CUDA float32 投影增加未融合的 TorchScript 分派。保留原算术次序、28 次二分和所有有效域判断，调用期间仅在当前跟踪线程设置 `torch.jit.optimized_execution(False)`，避免算子融合及浮点重排。CPU、float64、其他相机与串行路径仍使用参考实现。每个 device/dtype 只保留一个只读零标量。
- CLI、HTTP、Web 参数不变，准备线程默认仍为 2，保留 `xnav_execution=serial`。权重、精度、分辨率、阈值、词表、采样、batch、跟踪和提交顺序不变。

历史 GPU 元数据由跟踪线程在同一跟踪 CUDA 流上创建和使用，缓存内容只读，并保持引用直到缓存清空或任务结束；没有新增跨流写入或异步 CPU 回读。现有输入预取继续通过事件管理依赖和缓冲区生命周期，依据 [PyTorch 2.10 CUDA 流语义](https://docs.pytorch.org/docs/2.10/notes/cuda.html#cuda-streams) 核对。

## 计时口径

性能文件保留原字段，并增加持久化完成时刻、ACK 接收时刻、接收延迟、主线程分发延迟、几何实际后端、跟踪子阶段和缓存项数。

- `stages_ms` 是主机阶段跨度，包含等待；跟踪细分为可见性、关联、低 IoU 恢复、离屏恢复、历史投影与合并。子阶段允许嵌套，不应相加为阶段总和。
- `cuda_stages_ms` 是同一 CUDA 流两事件之间的跨度，包含主机提交间隙及流等待，不能当作纯内核耗时。
- 实际内核时间只从独立的 `torch.profiler` 诊断采样提取。诊断与正式吞吐测量分开；重叠内核的时长总和也不等于设备忙碌墙钟时间。
- 原 `committed_seconds`、`commit_latency_ms` 继续表示主线程处理提交回调的时刻与跨度。新增 `durable_seconds`、`durable_commit_latency_ms` 和 `steady_durable_throughput_fps` 以输出进程完成可靠写入的时刻为准；`ack_receive_delay_ms` 与 `ack_dispatch_delay_ms` 分别记录消息传输与主线程排队，不能把后者算成落盘延迟。
- 热路径不增加全局 CUDA 同步。阶段事件在任务结束后解析；跑分只在整次任务末尾同步，以包含已排队工作。

## 验证方法

在 RTX 5060 Laptop GPU（8 GiB）上，固定线程环境、现有 PyTorch/NumPy/OpenCV 版本以及缓存目录；其他应用保持运行。每次使用独立地图副本、权重缓存覆盖目录和输出目录，不写原地图或旧结果。正式验收使用完整地图、顺序配对，各 3 组，第二组交换执行先后；关闭诊断采样。

比较结果 JSON 的全部业务值（仅排除运行路径、耗时和 execution 诊断元数据），逐字节比较 `boxer_3dbbs.csv`、`boxer_3dbbs_tracks.csv`、`boxer_3dbbs_tracked.csv`、`owl_2dbbs.csv`、地图 `dino_features.csv`、`labels.csv`。比较包含每帧检测、特征、坐标、置信度、标签、关联、轨迹 ID、状态和别名，未使用浮点容差。

进程树 RSS 每秒采样；显存同时记录本任务 PyTorch 峰值与全设备采样值。全设备显存包含其他应用，不能作为本任务单独占用。

## 实测结果

完整 img7、img2 各三组顺序配对已完成，六组全部通过严格业务值和六 CSV 差分。img7 中位数降低 12.261%，达到样本目标；img2 三组均更快，中位数降低 4.296%，未出现稳定回退。独立功能、全量关联日志和缓存压力诊断也全部通过，详见后文。

| 地图 | 基线三次（秒） | 候选三次（秒） | 基线/候选中位数（秒） | 降低 |
|---|---|---|---|---|
| img7，278 帧 | 329.096 / 315.835 / 515.184 | 364.297 / 288.744 / 288.208 | 329.096 / 288.744 | **12.261%** |
| img2，469 帧 | 251.700 / 233.496 / 231.252 | 212.316 / 223.465 / 225.838 | 233.496 / 223.465 | **4.296%** |

img7 每组比较 1,580,754 个业务值，556 个图像观测及全部 2D/3D 检测、轨迹快照均一致；结果为 2,955 个 3D 检测、172 个确认对象。主目标的三组中位数比例达到 10%，但共享主机单次波动很大：第一组候选更慢，第三组基线显著变慢。因此这里报告的是规定三组样本，不能将百分比视为隔离环境的稳定保证。约定判据为 `1 - median(候选耗时) / median(基线耗时)`，结果是 12.261%；三个逐对降低比例分别为 -10.696%、8.577%、44.057%，其自身的中位数是 8.577%，这是另一种统计口径。完整原始结果见 `release-summary.json` 与 `release-img7-summary.json`。

早期局部基线 125.76 秒与回归测试发生重叠，该基线及由它计算的百分比不用于验收。后续局部及完整地图测量均不并行运行回归或诊断。

重新隔离采集的 img7 前 96 帧组合对照为 **106.26 → 91.94 秒（-13.47%）**，结果逐值和六 CSV 字节比较均通过。此结果仍不能替代完整地图三组中位数。各项优化的局部效果及相互影响以独立工件保存，不叠加各项百分比。

全部工件位于 `../../diagnostics/performance-20261109/`；运行脚本记录了执行选项和软硬件版本。

## 候选收敛

最初按 ACK、CPU 缓存和 PolynomialCamera 64 门槛组合的完整 img7 三组对照为：基线 283.62 / 253.29 / 272.83 秒，候选 255.44 / 246.60 / 269.82 秒；中位数 **272.83 → 255.44 秒（-6.37%）**。三组逐值结果和六 CSV 均一致，但未达到目标，因此未把这组结果当作验收通过。

后续诊断找到历史投影的冗余 GPU 相机标签回读。去掉回读并用相同字段字节构造几何键后，96 帧同轮对照为 112.00 → 104.43 秒（-6.76%），严格差分通过。64 与 256 门槛组合耗时分别为 104.43 与 104.29 秒，差别不足以支持降低默认门槛。

固定函数签名缓存虽然通过 146 项基础回归，但单项为 98.86 → 99.73 秒，没有收益，未纳入。NumPy 反投影局部数组复用保持 45 次二分和所有运算次序，三组共 36 帧准备数据字节相同，但端到端为 89.07 → 90.54 秒（慢 1.66%），也未纳入。生产数据准备继续使用原算法；Torch float32 反投影的 28 次迭代同样不变。

当前 CUPTI 12.8.90 返回 `CUPTI_ERROR_INVALID_DEVICE`，诊断没有取得 CUDA 内核活动。因此真实内核时间记为缺失（`kernel_stages_ms: null`），不能把 profiler 返回的设备时间 0 当作真实 GPU 耗时。主机阶段与 CUDA 流事件跨度仍分别报告。

共享锚点复用边界也已核对：img7 有 278 个不同的图像位姿/锚点组合，不能仅按 90 个 LiDAR 锚点复用可见点投影。所有独立图像仍参与准备、推理、跟踪和提交。

完整地图门槛补测纠正了局部样本的不足：同一组合的 256 门槛为 **241.27 秒**，64 门槛为 **232.49 秒**，整图再降 **3.64%**，全量结果和六 CSV 一致。因此最终候选启用纯 PolynomialCamera 组的 64 门槛，其他相机不变。

已有 PyTorch 的算子编译也做过隔离探针，显式关闭乘加融合和 CUDA Graph 后仍出现约 `1.9e-6` 的位级差异，故拒绝采用，没有改动生产数学实现或精度策略。

## 未融合算子分派验证

历史 PolynomialCamera 的小算子反复从 Python 提交。隔离微测在关闭执行器优化后保留原运算结果，并减少 Python 分派开销；没有使用 CUDA Graph 或 `torch.compile`。执行器优化开关的线程隔离及异常恢复由实际测试验证，推理线程设置保持原值。PyTorch 2.10 对 `torch.jit.script` 给出弃用提示；本轮沿用现有环境，后续迁移须重新通过严格数值差分。

真实模型的独立 160 帧对照，以已有 ACK/CPU 缓存/64 门槛版本为参考：**159.0377 → 146.9476 秒（-7.6020%）**。752,480 个业务值及六个 CSV 严格相同。该局部收益不等同于相对最初冻结基线的完整地图收益，也不与其他改动的百分比直接相加。详见 `scripted-prefix160-summary.json`。

最终候选已冻结到 `source-release`，SHA-256 清单为 `release-manifest.json`。回归为 **534 passed, 1 skipped**；跳过的是已经由正向测试覆盖的 CUDA float32 PolynomialCamera 参考回退参数组合。测试覆盖六种相机的 CPU/CUDA、float32/float64 回退，以及不同批次、畸变开关、NaN、无效域的位级结果。

img7 其他口径：含模型加载的 `wall_seconds` 中位数 **338.178 → 302.293 秒（-10.611%）**；含解释器启动、地图隔离设置和退出的 `process_wall_seconds` 为 **342.021 → 307.094 秒（-10.212%）**。模型加载本身中位数 9.184 / 9.790 秒。

img7 进程树 RSS 峰值中位数 3861.3 / 3813.4 MiB；PyTorch 显存分配峰值中位数 783.8 / 779.9 MiB，保留峰值 1294.0 / 1332.0 MiB。全设备利用率包含其他应用；当前没有足够内核活动采样来把这些数字归为本任务的设备忙碌时间。

## 最终功能与生命周期验证

最终冻结候选的 CUDA 回归为 **534 passed, 1 skipped（93.63 秒）**。唯一跳过项是回退参数表中的 CUDA float32 PolynomialCamera 正向组合，该路径另有专门的逐位对照测试。回归覆盖 ACK 延迟、重复和乱序、输出进程崩溃、回调异常、停止、满队列、终止消息、正常收尾及幂等关闭；覆盖六种相机、63/64/65 和 255/256 条轨迹、边界点、空点云，以及合并后标签和代表框变化。所有真实整图候选运行记录的 `max_uncommitted_frames` 和 `max_inflight_frames` 均为 2，准备线程仍为 2。

独立真实模型功能对照均通过业务值、六 CSV 和关联事件日志比较：

| 功能 | 对照帧数 | 结果 |
|---|---:|---|
| 原生视图及预览 | 32 | PASS；JPEG 字节和视频解码后 32 帧也一致 |
| 虚拟视图 | 16 | PASS |
| 串行回退 | 16 | PASS |
| 2D 缓存重放 | 16 | PASS；同进程完整运行后再重放 |
| 3D 缓存重放 | 32 | PASS |

完整 img7 另做一组带全量关联日志的诊断对照，278 帧、1,580,754 个业务值与六 CSV 全部一致，match/create/merge 事件、最终 support frames 和历史成员均一致。该诊断任务耗时 **284.619 → 263.189 秒（降低 7.53%）**，不参与关闭诊断后的正式三组吞吐验收。功能和关联证据分别见 `extra-checks.json`、`profile-release-comparison.json`。

缓存压力验证包含 10,000 次有向几何查询，IoU 和证据缓存均限制为 512 项。该压力循环没有历史观测，因此投影缓存为 0；实际完整 img7 诊断中的投影缓存峰值为 512，IoU 峰值为 180。历史 GPU 元数据压力测试重复两轮，每轮 1,000 / 2,000 条观测分别占 1,024,000 / 2,048,000 字节；`reset()` 后新增分配量回到 0。历史元数据随保留观测线性增长，配对缓存有界，不能将其描述为全部缓存恒定内存。证据见 `cache-stress.json`。

本轮涉及文件的 Ruff 检查相对冻结基线没有新增问题；基线 18 项、当前 15 项保留问题均属于原有代码，未宣称整个仓库零问题。范围内 `git diff --check` 通过。完整命令和结果见 `regression-evidence.json`、`ruff-comparison.json`。原有未提交及未跟踪文件均保留；源码冻结期间另有 Docker 和部署文档修改，已单独记录在 `release-external-changes.json`，未归入本轮性能实现。
